一個網站的最小組成

Frontend前端使用者看得到、摸得到的那一層。負責畫面、互動、輸入。

跑在使用者的瀏覽器裡。
Backend後端商業邏輯與權限的守門人。決定資料給不給、怎麼給。

跑在你的伺服器上。
Database資料庫資料真正住的地方。關機、重開都不會消失。

通常跟後端放在一起或旁邊。
nutc@workshop:~$ describe frontend

前端：使用者看得到的那一層

  • 把資料變成畫面HTML 結構、CSS 樣式、JavaScript 互動
  • 收集使用者的輸入表單、按鈕、捲動
  • 向後端要資料用 fetch() 發出請求，拿到 JSON 再渲染
關鍵認知

前端的程式碼全部都在使用者電腦上，任何人按下 F12 都看得到、改得動。

所以「前端有做檢查」從來不等於「安全」。這是今天最重要的觀念之一。

// 如果登入判斷寫在前端…… if (password === "admin123") { showProfile(); // ← 任何人按 F12 就看到密碼了 } // ← 甚至可以直接改成 if (true)
守門驗證身分與權限你是誰？你能看哪些資料？
邏輯執行商業規則扣庫存、算運費、發通知
看守唯一能碰資料庫的人前端永遠不該直接連資料庫
一句話：後端存在的理由，是因為前端跑在別人的電腦上，不能被信任。

資料庫：資料真正住的地方

  • 持久化 Persistence程式關掉、機器重開，資料還在

  • 一致性 Consistency轉帳時不會出現「扣了但沒入帳」

它們怎麼講話？HTTP

CLIENT前端我想要 /api/me 的資料，這是我的通行證
──▶
SERVER後端通行證有效，這是你的資料，狀態 200
──▶
CLIENT前端收到 JSON，渲染成畫面
API 是一問一答的。後端不能主動跟前端說話 —— 它只能等，然後回答。這個限制會影響你之後所有的設計。
nutc@workshop:~$ curl -v https://api.example.com/api/me

一個 HTTP 請求長什麼樣

POST /api/login HTTP/1.1 ← 方法 + 路徑 Host: api.example.com Content-Type: application/json ← 我送的是 JSON Authorization: Bearer eyJhbGci... ← 通行證放這裡 {"username": "jase", "password": "1234"} ← Body，真正的資料
GET拿資料不改變任何東西
POST新增 / 送出登入、註冊、下訂單
PUT更新修改既有資料
DELETE刪除移除資料
nutc@workshop:~$ http --status-codes

回應與狀態碼

開頭意思你會遇到的除錯方向
2xx成功200 OK · 201 Created沒事，繼續
3xx轉址301 搬家了 · 304 沒變過通常不用管
4xx你（前端）錯了400 格式錯 · 401 沒登入 · 403 沒權限 · 404 找不到檢查你送出的請求
5xx我（後端）錯了500 程式爆炸 · 502 上游掛了去看伺服器的錯誤日誌

反向代理：所有人的第一站

瀏覽器 ──▶ Nginx ─┬─▶ 後端 A ／api/* 處理 API :443 ├─▶ 後端 B ／admin/* 後台服務 └─▶ 靜態檔 ／* HTML、圖片
  • 對外只開一個門後面有幾台機器、跑什麼語言，外面完全不知道
  • HTTPS 在這裡處理憑證裝一次就好，後面的服務可以繼續講 HTTP
  • 擋掉明顯的壞請求流量太大時先在這一層限流
nutc@workshop:~$ describe cache

快取：重複的問題不要重複算

沒有快取每次都算一遍10,000 人看首頁熱門排行
→ 資料庫被查 10,000 次
→ 每次 200 ms

資料庫先陣亡
有快取算一次，存 60 秒第 1 人：查資料庫，存進 Redis
第 2–10,000 人：直接讀 Redis
→ 每次 2 ms

快 100 倍
代價是「資料可能有點舊」。熱門排行慢 60 秒沒關係，銀行餘額就不行 —— 什麼能快取，是設計決策。
nutc@workshop:~$ trace --full "https://myapp.com/profile"

一個請求的完整旅程

01 瀏覽器 檢查快取，沒有 → 準備發出請求 02 DNS myapp.com 是誰？ → 203.0.113.45 03 TCP+TLS 跟那個 IP 建立連線並交換憑證，鎖頭出現 04 CDN 圖片、CSS 就近給你，不勞煩主機 05 Nginx 看路徑 /profile → 轉給後端服務 06 後端 驗證 token → 你是 jase，有權限 07 快取 Redis 有這筆資料嗎？沒有 → 往下 08 資料庫 SELECT * FROM users WHERE id=7 09 後端 組成 JSON，回傳 200，順便寫進快取 10 瀏覽器 收到 JSON → 渲染成畫面 → 你看到了
全部發生在約 0.3 秒內。今天你會親手做出第 06 到第 09 步。

問題來了：哪一個是最新的？

而且，如果你想知道「上週三那版的第三章寫了什麼」，現在還找得回來嗎？

nutc@workshop:~$ why git

版本控制到底解決什麼

紀錄每一次改動都留底誰、什麼時候、改了哪幾行、為什麼改。而且只留一份檔案。
回溯隨時回到任何一天「昨天還好好的」不再是絕望的一句話，而是一個指令。
分身安全地亂搞開一條分支試新功能，搞砸了就丟掉，主線完全不受影響。
對一個人做專案的你，最有用的是第三點。有了分支，你才敢大膽改。
nutc@workshop:~$ git --explain-areas

Git 的三個區域

WORKING DIR工作目錄你正在編輯的檔案

= 現場
git add ▶
STAGING暫存區你決定這次要記錄的改動

= 取景框
git commit ▶
REPOSITORY儲存庫永久保存的歷史紀錄

= 沖洗好的相片
為什麼要有中間那層？因為你可能一次改了五個檔案，但其中只有三個屬於同一件事。暫存區讓你把它們分成兩次 commit。
nutc@workshop:~$ git --core-commands

核心四動作，先會這些就好

指令做什麼白話
git add .把改動放進暫存區「這些我要記錄下來」
git commit -m "訊息"寫進本機的歷史「存檔，並寫一句說明」
git push推上遠端（GitHub）「上傳到雲端備份」
git pull拉下遠端的更新「同步別人的進度」
還有一個你會用到一百次的：git status —— 不確定現在是什麼狀態時就打它，它連下一步該做什麼都會提示你。
nutc@workshop:~$ git config --setup

第一次使用：設定你是誰

# 整台電腦只要設定一次，之後每個專案都會用這個身分 git config --global user.name "Your Name" git config --global user.email "you@example.com" # 順便把預設分支名稱設成 main（現在的慣例） git config --global init.defaultBranch main # 確認一下（應該印出你剛剛設定的值） git config user.name git config user.email
email 建議用你 GitHub 註冊的那個。否則 GitHub 不會把 commit 算在你的貢獻紀錄上。

nutc@workshop:~$ git branch --explain

分支：安全地亂搞

main ●───●───●───────────● ← 隨時都能跑的穩定版 ╲ ╱ login-api ●───●───● ← 在這裡大膽實驗 開分支 合併回去
git switch -c login-api # 開一條新分支並跳過去 # ……在這裡改東改西，commit 好幾次…… git switch main # 跳回主線 git merge login-api # 把成果合併進來 git branch -d login-api # 收工，刪掉分支
什麼時候該開分支？當你要做的事「可能會做壞」或「做到一半」時。今天下午加功能就用這個方式。
nutc@workshop:~$ git merge --conflict

衝突：兩個人改了同一行

<<<<<<< HEAD ← 這是你的版本 PORT = 8000 ======= ← 分隔線 PORT = 3000 >>>>>>> login-api ← 這是分支的版本
  • 這不是錯誤訊息Git 只是在問你：這一行要留哪個？它不敢替你決定
  • 做法：留下你要的內容，連同那三行標記一起刪掉
  • 然後 git add → git commit，衝突就解決了
VS Code 會幫你標色並提供選擇按鈕，不必手動刪。
nutc@workshop:~$ code . --show-scm

在 VS Code 裡做完全部的事

  • 左側第三個圖示：原始檔控制快捷鍵 Ctrl/Cmd + Shift + G
