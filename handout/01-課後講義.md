## 主題 1 · 資訊系統架構

### 三層式架構

一個網站的最小組成只有三塊：

| | 負責什麼 | 跑在哪 |
| --- | --- | --- |
| **前端** Frontend | 畫面、互動、收集輸入 | **使用者的瀏覽器** |
| **後端** Backend | 商業邏輯、權限、決定資料給不給 | 你的伺服器 |
| **資料庫** Database | 持久化保存資料 | 通常跟後端放一起或旁邊 |

### 為什麼不能只有前端

前端的程式碼**全部都在使用者電腦上**，任何人按 F12 都看得到、改得動。

```javascript
// 如果登入判斷寫在前端……
if (password === "admin123") {
  showProfile();   // ← 按 F12 就看到密碼了
}                  // ← 甚至可以直接改成 if (true)
```

> **後端存在的理由，是因為前端跑在別人的電腦上，不能被信任。**

所以「前端有做檢查」從來不等於「安全」。所有真正的檢查都必須在後端**再做一次**。

### HTTP：三層之間唯一的語言

HTTP 是**一問一答**的。後端不能主動跟前端說話，它只能等，然後回答。

一個請求包含四個部分：

```http
POST /api/login HTTP/1.1              ← 方法 + 路徑
Host: api.example.com
Content-Type: application/json        ← 標頭：我送的是 JSON
Authorization: Bearer eyJhbGci...     ← 通行證放這裡

{"username": "jase", "password": "1234"}   ← Body，真正的資料
```

| 方法 | 用途 |
| --- | --- |
| `GET` | 拿資料，不改變任何東西 |
| `POST` | 新增、送出（登入、註冊、下訂單） |
| `PUT` | 更新既有資料 |
| `DELETE` | 刪除 |

### 狀態碼

| 開頭 | 意思 | 常見的 |
| --- | --- | --- |
| 2xx | 成功 | 200 OK · 201 Created |
| 3xx | 轉址 | 301 搬家了 · 304 沒變過 |
| 4xx | **你（前端）錯了** | 400 格式錯 · 401 沒登入 · 403 沒權限 · 404 找不到 |
| 5xx | **後端錯了** | 500 程式爆炸 · 502 上游掛了 |

**除錯第一步永遠是先看狀態碼。** 401 和 500 的處理方向完全不同，看錯了會找一小時。

### 後端周圍還住著誰

這些不是現在要學的，是要知道它們存在、叫什麼名字：

| 分類 | 角色 | 解決什麼問題 |
| --- | --- | --- |
| 入口 | **反向代理**（Nginx） | 對外只開一扇門，HTTPS 在這層處理 |
| 入口 | API Gateway | 限流、認證、路由分派 |
| 加速 | **快取**（Redis） | 重複的問題不要重複算 |
| 加速 | CDN | 圖片、CSS 就近供應 |
| 解耦 | 訊息佇列 | 慢的事情排隊做 |
| 擴張 | 負載平衡 | 一台不夠就分給十台 |
| 定位 | DNS | 把網域名稱翻成 IP |
| 安全 | TLS 憑證 | 網址列那個鎖頭 |

### 一個請求的完整旅程

```
01 瀏覽器  檢查快取，沒有 → 準備發出請求
02 DNS     myapp.com 是誰？ → 203.0.113.45
03 TCP+TLS 建立連線並交換憑證，鎖頭出現
04 CDN     圖片、CSS 就近給你
05 Nginx   看路徑 → 轉給後端服務
06 後端    驗證 token → 你是 jase，有權限          ┐
07 快取    Redis 有這筆嗎？沒有 → 往下              │ 這四步
08 資料庫  SELECT * FROM users WHERE id=7          │ 是你今天
09 後端    組成 JSON，回 200，順便寫進快取          ┘ 親手做的
10 瀏覽器  收到 JSON → 渲染成畫面
```

全部發生在約 **0.3 秒**內。

## 主題 2 · 用 Git 管理專案

### Git 的三個區域

| 區域 | 是什麼 | 比喻 |
| --- | --- | --- |
| **工作目錄** Working Dir | 你正在編輯的檔案 | 現場 |
| **暫存區** Staging | 你決定這次要記錄的改動 | 取景框 |
| **儲存庫** Repository | 永久保存的歷史紀錄 | 沖洗好的相片 |

`git add` 把東西從左邊送到中間，`git commit` 從中間送到右邊。

**為什麼要有中間那層？** 因為你可能一次改了五個檔案，但只有三個屬於同一件事。暫存區讓你把它們分成兩次 commit。

### 核心四動作

```bash
git add .                 # 「這些我要記錄下來」
git commit -m "訊息"       # 「存檔，並寫一句說明」
git push                  # 「上傳到雲端備份」
git pull                  # 「同步別人的進度」
```

還有一個你會用到一百次的：**`git status`** —— 不確定現在是什麼狀態時就打它，它連下一步該做什麼都會提示你。

### commit message 怎麼寫

| ❌ 半年後看不懂 | ✓ 半年後會感謝 |
| --- | --- |
| `update` | `新增登入 API` |
| `fix` | `修正 token 過期未檢查的問題` |
| `改好了` | `把假資料換成 SQLite` |
| `最終版` | `調整 CORS 允許來源` |

**訣竅**：寫「為什麼改」，不要寫「改了什麼」。改了什麼看 `git diff` 就知道了，為什麼改只有你知道。

### 分支

```
main     ●───●───●───────────●   ← 隨時都能跑的穩定版
              ╲         ╱
login-api      ●───●───●         ← 在這裡大膽實驗
```

```bash
git switch -c login-api    # 開一條新分支並跳過去
git switch main            # 跳回主線
git merge login-api        # 把成果合併進來
git branch -d login-api    # 收工，刪掉分支
```

**什麼時候該開分支？** 當你要做的事「可能會做壞」或「做到一半」時。

### 衝突不是錯誤

```
<<<<<<< HEAD              ← 這是你的版本
PORT = 8000
=======                   ← 分隔線
PORT = 3000
>>>>>>> login-api         ← 這是分支的版本
```

Git 只是在問你：這一行要留哪個？**它不敢替你決定。**
留下你要的內容，連同那三行標記一起刪掉，然後 `git add` → `git commit`。

### Git Graph

VS Code 擴充套件（作者 mhutchie），把 commit 歷史變成一張圖：

- 每個**圓點** = 一個 commit，點下去看那次改了哪幾行
- 每條**線** = 一條分支，分岔是開分支，匯流是 merge
- **彩色標籤** = 分支名與遠端位置，一眼看出本機跟 GitHub 差多少

## 主題 3 · 用 Python 手寫後端

完整程式碼見 [`../demo/`](../demo/)，以下是重點。

### 伺服器是什麼

一個**永遠不結束、一直在等**的程式。`Ctrl + C` 才會停。

- **IP 位址** = 大樓地址（`127.0.0.1` 是「我自己這台」）
- **Port** = 門牌號碼（0–65535，同一個 port 只能有一個程式在聽）

`Address already in use` 就是這麼來的 —— 上一個伺服器還活著。

### 為什麼要用框架

不用框架的話，判斷路徑、讀 Content-Length、解析 JSON、檢查欄位型別，
**每個專案都要重做一次**。框架把這些包好了。

```python
from fastapi import FastAPI
app = FastAPI()

@app.get("/api/hello")          # 路由
def hello():
    return {"message": "Hello"}  # dict 自動變 JSON
```

啟動：`uvicorn main:app --reload`（`main` 是檔名、`app` 是變數名）

**免費附送 `/docs`** —— 自動產生的 API 文件，還能直接測試。
每寫一支 API 就回去測一次，這是最省時間的除錯習慣。

### Pydantic：型別標註就是設定

```python
class LoginIn(BaseModel):
    username: str
    password: str

@app.post("/api/login")
def login(data: LoginIn):        # ← 這行就是全部的設定
    return {"got": data.username}
```

少送欄位會自動回 **422**，你一行檢查都沒寫。

### 登入 API 的兩個設計決策

```python
if not user or user["password"] != data.password:
    raise HTTPException(status_code=401, detail="帳號或密碼錯誤")
```

1. **帳號不存在和密碼錯誤，回同一個訊息。**
   分開告知等於幫攻擊者確認哪些帳號存在。

2. **回 token，不要每次送密碼。**
   密碼只在登入時出現一次；token 可設有效期，外洩了作廢就好。

### CORS

前端在 5500、後端在 8000，瀏覽器認定這是兩個不同的**來源**，預設擋下來。

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://127.0.0.1:5500"],   # 不要寫 "*"
    allow_methods=["*"],
    allow_headers=["*"],
)
```

**這是瀏覽器擋的，不是後端壞了。** `curl` 打同一支 API 會成功 —— 因為 curl 不是瀏覽器。

同源政策存在的理由：否則惡意網站可以偷偷用你的身分去打別人的 API。

### 受保護的 API

```python
@app.get("/api/me")
def me(authorization: str = Header(default="")):
    token = authorization.replace("Bearer ", "")
    username = TOKENS.get(token)
    if not username:
        raise HTTPException(status_code=401, detail="請先登入")
    u = USERS[username]
    return {"username": username, "name": u["name"], "dept": u["dept"]}
    # 注意：沒有回傳 password。永遠不要回傳密碼。
```

前端可以自己跳到 `profile.html`，但**沒有有效 token，它一筆資料也拿不到**。
這就是「後端才是守門人」的意思。

### 換成 SQLite

```python
con.execute("SELECT * FROM users WHERE username = ?", (username,))   # ✓
con.execute("SELECT * FROM users WHERE username = '" + username + "'")  # ✗ SQL 注入
```

那個 `?` 很重要。改完之後，**API 規格和前端程式碼一行都不用動** —— 這就是分層的價值。

## 主題 4 · 網際網路與發佈網站

### localhost 是什麼

| | |
| --- | --- |
| `127.0.0.1` | 「我自己」。每台電腦都有，指的都是它自己 |
| `localhost` | `127.0.0.1` 的小名，不需要查 DNS |
| 封包去哪了 | **根本沒出門**，在網卡裡繞一圈就回來了 |

所以「我的網站做好了」目前只對你成立。

### 讓同學連得到

```bash
ipconfig getifaddr en0                       # macOS，查你的 IP
uvicorn main:app --host 0.0.0.0 --port 8000  # 聽所有網卡，不只聽自己
# 同學打 http://192.168.1.37:8000 ← 用你的 IP，不是 localhost
```

### 網址的解剖

```
https:// api.myapp.com : 443 /profile
└──┬──┘ └─────┬──────┘ └─┬─┘ └──┬───┘
  協定     網域名稱      Port   路徑
            ↓ 交給 DNS 查
        203.0.113.45   ← 真正要連的地址
```

網域名稱是給人記的，電腦只認 IP。http 預設 port 80、https 預設 443，所以網址上通常看不到 port。

### HTTPS 保護什麼、不保護什麼

| ✓ 保護 | ✗ 不保護 |
| --- | --- |
| 咖啡廳 Wi-Fi 上的人看不到你的密碼 | **對方是好人** |
| 中途沒人能偷改內容 | 詐騙網站也能申請憑證 |
| 你連到的確實是那個網域 | 資料到對方手上之後就管不著了 |

**有鎖頭 ≠ 這個網站可以信任。**

### 上線前：不要把鑰匙上傳到 GitHub

```python
SECRET_KEY = "my-super-secret-1234"                  # ❌ 絕對不要
SECRET_KEY = os.environ.get("SECRET_KEY", "dev")     # ✓ 從環境變數讀
```

`.gitignore` 一定要有：`.venv/`、`.env`、`*.db`

> GitHub 上的秘密會被機器人在**幾分鐘內**掃到。
> 已經推上去的話，**改密碼比刪 commit 重要得多**。

### 發佈的三條路

| 做法 | 難度 | 適合 |
| --- | --- | --- |
| 內網分享（`--host 0.0.0.0`） | 最簡單 | 教室 demo、隊友測試 |
| **PaaS 平台**（連 GitHub，push 自動部署） | 簡單 | **學生專題、作品集** |
| 自己租 VPS（裝 Python、Nginx、憑證、防火牆） | 困難 | 要完全掌控時 |

### 部署前：從兩個服務變成一個

本機開發時前端在 5500、後端在 8000，是**兩個來源**，所以要設 CORS。
正式環境讓 FastAPI 自己供應前端，變成**一個服務、同一個來源**，CORS 問題自動消失。

```python
# main.py 最後面（一定要在所有 API 之後，否則 API 會被攔截）
from fastapi.staticfiles import StaticFiles
app.mount("/", StaticFiles(directory="web", html=True), name="web")
```

```javascript
// web/login.js、profile.js 的第一行
// 本機在 5500 要指定後端；部署後同源，用相對路徑
const API = location.port === "5500" ? "http://127.0.0.1:8000" : "";
```

### 部署到 Render

```bash
pip freeze > requirements.txt     # 讓平台知道要裝什麼
git add .
git commit -m "準備部署"
git push
```

到 [render.com](https://render.com) 用 GitHub 登入 → New → Web Service → 選 repo，填三個欄位：

| 欄位 | 填什麼 |
| --- | --- |
| Language | `Python 3` |
| Build Command | `pip install -r requirements.txt` |
| Start Command | `uvicorn main:app --host 0.0.0.0 --port $PORT` |

方案選 **Free** → Create Web Service。等 2–5 分鐘變成 Live，就拿到網址了。

### 免費方案的三個坑

| | 現象 | 為什麼 |
| --- | --- | --- |
| **坑 1** | 第一次打開要等 30–60 秒 | 閒置太久會自動停機，那是在冷啟動，不是壞了 |
| **坑 2** | 重啟後資料全不見 | 免費方案**沒有持久磁碟**，`app.db` 會消失 |
| **坑 3** | 流程跟講義不一樣 | 平台的免費方案規則隨時在調整 |

坑 2 才是重點：要真的保存資料，必須用**外部資料庫**，
不能用跟服務一起消失的 SQLite 檔。程式碼見 [`../demo/step-9-deploy/`](../demo/step-9-deploy/)。

### 上線後檢查清單

- [ ] 用**手機的行動網路**打開（不是教室 Wi-Fi，那不算真的對外）
- [ ] 網址列有鎖頭
- [ ] 登入流程完整走一次（正確與錯誤帳密都試）
- [ ] 直接打 `profile.html` 會被踢回登入頁
- [ ] GitHub 上沒有密碼、金鑰、`.env`
- [ ] `allow_origins` 沒有留著 `"*"`

## 主題 5 · 用 AI 做到同樣的成果

### 核心主張

> **AI 不會讓你不用懂，它讓懂的人快十倍。**

| 不懂的人用 AI | 懂的人用 AI |
| --- | --- |
| 拿到一坨會動的程式碼 | 拿到一份初稿 |
| 不知道對不對、安不安全 | 看得懂、挑得出問題 |
| 一改就壞，出錯只能重問 | 知道該補什麼、能精準描述下一步 |

### 四段式骨架

```
【角色】你是 ________ 工程師，對象是 ________。
【目標】________（一次只講一件事）
【規格】路徑 / 輸入 / 成功回什麼 / 失敗回什麼
【限制】不要用 ________（我還沒學）；只做這一件事
【輸出】完整檔案 + 執行指令 + 測試方式
```

**最常被省略、也最關鍵的是「限制」。**

### 兩條鐵則

1. **一次只要一步** —— 寫一支 API → 跑起來 → 確認對 → 再問下一步
2. **給規格，不要給願望** —— 「做個好用的登入」是願望；「POST /api/login，成功 200 回 token」是規格

### 貼上之前的三個必問

1. 這段程式碼，**哪一行在做驗證**？
2. 使用者送出空密碼、超長字串會怎樣？
3. 它有沒有**回傳不該回傳的東西**？

三題都答得出來，才按下貼上。

### AI 最常出的四種錯

| | 症狀 | 怎麼驗證 |
| --- | --- | --- |
| **幻覺** | 發明不存在的套件、函式，講得很有自信 | 去官方文件搜尋 |
| **過時** | 三年前的寫法，能跑但已淘汰 | 問「這是目前建議的寫法嗎？」 |
| **不安全的預設** | `allow_origins=["*"]`、密碼明文 | 對照上線檢查清單 |
| **過度設計** | 你要一支 API，它給你一套架構 | 看不懂就是不能用 |

### 出錯時怎麼問

四樣東西**缺一不可**：① 完整指令 ② 完整錯誤訊息含 Traceback ③ 環境版本 ④ 你期待的結果。

最後加一句：**「請先說明這個錯誤的原因，再給修正後的程式碼。」**
先解釋，你才學得到東西。

## 主題 6 · 用 AI 進行測試

### 為什麼要測試

> 測試不是為了證明程式對，是為了讓你**敢改**。

這跟 Git 分支的道理完全一樣。

### 測試的三層

| 層 | 測什麼 | 特性 |
| --- | --- | --- |
| 單元 Unit | 一個函式 | 快、多、便宜 |
| **API** | 一支 API 的輸入輸出 | **後端投報率最高** |
| 端對端 E2E | 模擬真人操作瀏覽器 | 慢、貴、最接近真實 |

### pytest 的長相

```python
from fastapi.testclient import TestClient
from main import app

client = TestClient(app)          # 一個假的瀏覽器，不用真的開伺服器

def test_login_success():          # 函式名一定要 test_ 開頭
    """正確的帳號密碼應該拿到 token"""
    r = client.post("/api/login", json={"username": "jase", "password": "1234"})
    assert r.status_code == 200    # assert = 我主張……
    assert "token" in r.json()     # 不成立就算這個測試失敗
```

執行：`pytest -v`

### 看懂失敗訊息

```
FAILED test_main.py::test_login_wrong_password
E       assert 403 == 401
══ 1 failed, 6 passed in 0.42s ══
```

三件事：**哪個測試掛了**、**期待什麼**、**實際拿到什麼**。
其他六個還是綠的 —— 問題被縮小到一個地方了。

### 讓 AI 補你想不到的

提示詞最後加一句：**「請另外列出你想到、但我沒列到的測試案例。」**

它通常會補上：大小寫不同的帳號、前後空白、Unicode 密碼、連續登入 token 會不會重複、錯誤訊息有沒有洩漏帳號存在。

**這就是 AI 在測試上的真正價值：它不會累，也沒有「應該不會有人這樣用」的盲點。**

### 請 AI 修 bug 的正確順序

1. **先寫測試**，讓失敗可以被重現
2. 貼完整訊息（測試碼 + 失敗輸出 + 程式碼）
3. 要它**先解釋**為什麼會錯
4. **再跑一次測試**，綠了才算修好

沒有第 1 步，你永遠不知道它到底修好了沒。「看起來好了」不是驗收標準。

### 覆蓋率的陷阱

| 它告訴你 | 它不告訴你 |
| --- | --- |
| 哪幾行從來沒被跑過 | **跑過 ≠ 測對了** |

每一行都跑過，但你只檢查「有回應」沒檢查「回應正確」—— 覆蓋率一樣是 100%。

**把它當地圖，不要當成績。** 覆蓋率低一定有問題，覆蓋率高不代表沒問題。
