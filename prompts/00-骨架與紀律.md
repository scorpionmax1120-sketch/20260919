# 提示詞的骨架與兩條鐵則

## 四段式骨架

```
【角色】你是 ________ 工程師，對象是 ________。

【目標】________（一次只講一件事）

【規格】
- 路徑：
- 輸入：
- 成功回什麼：
- 失敗回什麼：

【限制】
- 不要用 ________（我還沒學）
- 只做這一件事，不要順便加功能
- 每段加繁體中文註解

【輸出】完整檔案 + 執行指令 + 測試方式
```

**最常被省略、也最關鍵的是「限制」。** 少了它，你會拿到一個「很厲害但你看不懂」的版本。

## 鐵則一：一次只要一步

寫一支 API → 跑起來 → 確認對 → 再問下一步。

一次要五個功能，五個都有小問題，你會分不清是哪裡壞的。

## 鐵則二：給規格，不要給願望

| | |
| --- | --- |
| ❌ 願望 | 「做個好用的登入」 |
| ✓ 規格 | 「POST /api/login，成功 200 回 token，失敗 401 回『帳號或密碼錯誤』」 |

## 對照：同一個需求，兩種問法

**❌ 你會拿到災難**

> 幫我做一個登入系統

它會給你 JWT、SQLAlchemy、Alembic、Docker、OAuth2 —— 一個你完全看不懂也跑不起來的專案，而且你連從哪裡開始除錯都不知道。

**✓ 你會拿到能用的**

> 用 FastAPI 寫一支 POST /api/login，輸入 username 和 password，成功回 token，失敗回 401，資料先用 dict 假資料，不要用 JWT

差別不在 AI 有多強，在你把需求講得多清楚。
